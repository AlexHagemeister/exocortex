# .state/ — pipeline bookkeeping

Skill-owned only: sweep cursors, ingest hash ledger, deleted-notes list, query-traffic log, lint reports and queue, digest compiles, review markers, system-review reports. Excluded from ingestion and from the bundle; never ships. Files here are working state, not knowledge — nothing in this folder is a source or a claim.

**issues/** — friction-log issue files, one per issue with `status` frontmatter; ISSUES.md at the vault root is their derived open-index (convention lives there). Resolved files stay as history.

**reviews/** — whole-system review reports, one per run; the score trend across them is the system's health curve.

**maintainer.lock** — advisory concurrency lock for scheduled maintainer runs (added 2026-07-16, user-approved). A running scheduled task writes `<task-name> <ISO 8601 timestamp> <pid>` here at start (the writing process's own PID, e.g. `$$` from its shell) and deletes it at end. A run finding a held lock checks the holder's liveness with `kill -0 <pid>`: if the holder is dead, clear the lock with a day-log note and proceed; if alive, stand down and retry on the next schedule. A lock in the old two-field format or with an unreadable PID falls back to the age rule: under 2 hours old, stand down; 2+ hours old, treat as a crashed run's residue and replace (with a log note) (liveness check added 2026-08-31, user-approved). Reporting writes are never lock-gated: appending a line to `wiki/log/<today>.md` or creating a new file in `.state/issues/` proceeds under any lock, because a run that stands down silently is indistinguishable from one that never fired (added 2026-08-17). A run that stands down because the lock is held writes one day-log line, "stood down, lock held by <holder>", before exiting, which preserves that same fired-vs-never-fired distinction and makes held-lock frequency visible (added 2026-08-27). A run resuming after an interruption re-reads the lock before its next write and stands down if it is no longer the holder, since interrupted runs are the usual way a lock outlives its owner (added 2026-08-17). Interactive sessions are not bound by the lock but should be aware of it.
